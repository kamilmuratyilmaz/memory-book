1Introduction

The user can change a book in two ways. The user can edit the pages with the mouse. Or the user can write a request in the chat panel, for example "Make the whole book feel more vintage".

AG-UI (Agent–User Interaction protocol) is an open protocol. It sets how a user interface and an AI agent exchange data. The browser sends one HTTP request. The server sends back a stream of small events. Each event has a type, for example TEXT_MESSAGE_CONTENT or STATE_DELTA.

With these events, the browser can show the work of the agent while the agent works:

  • The reply of the model, word by word.
  • A summary of the reasoning of the model.
  • A checklist of the planned changes and their progress.
  • Each change to the book, as a small JSON Patch.
  • A request for approval before a large change.
  • The token usage of the run.

Memory Book uses the official AG-UI packages: ag-ui-protocol on the server (Python) and @ag-ui/client in the browser (TypeScript).

2Terms

TermMeaning in this system
RunOne request from the user, or one approval decision. One run is one HTTP request and one event stream. One run is also one undo step in the editor.
ThreadThe conversation of one book. Its identifier is book-<book id>. The server keeps the thread in PostgreSQL.
EventOne message in the stream from the server, for example RUN_STARTED. The server sends each event as one Server-Sent Events (SSE) line.
StateThe data that the browser and the agent share. In Memory Book, the state is {"book": MemoryBook}.
PlanA list of typed operations that the model makes, for example set_text or delete_page. The model cannot do other actions.
Tool callOne operation of the plan, sent as TOOL_CALL_* events. A frontend tool is a tool that the browser does (paragraph 8).
ActivityA message that shows progress. Here it is the checklist of planned changes (book-changes).
InterruptA stop of the run to get a decision from the user. The next run sends the decision as resume.

3Components

Figure 1 shows the components of the chat editing function. Blue boxes are in the browser. Brown boxes are the AG-UI part of the server. Grey boxes are other modules and services.

Browser

ChatPanel.tsx shows the conversation. It uses HttpAgent to start a run and to receive the events. HttpAgent applies each state patch. Then the chat panel gives the new book to the editor.

Server

agui.py is the AG-UI part of the server. It reads the run input, gets a plan from the model, applies the plan and sends the events. It does not change the book in the database. The editor saves the book.

5Shared state and patches

The browser and the agent share one state object: {"book": …}. The browser sends the full book one time, in the run input. After each operation, the server compares the book before and after the operation. Then it sends only the differences as a STATE_DELTA event.

A STATE_DELTA contains JSON Patch operations (RFC 6902). Figure 3 shows a real example. The plan changes the theme and moves page "pg_c" to position 1.

json_diff compares lists of objects by their id field. Thus a moved page is one move operation, and a deleted page is one remove operation. A simple index comparison would send many replace operations for the same change.

HttpAgent applies each patch to its copy of the state. Then it calls onStateChanged (ChatPanel.tsx:107). The chat panel gives the new book to the editor. All the patches of one run make one undo step.

CAUTIONThe server changes only the copy of the book in the run. The editor saves the book with its usual autosave. If the browser closes during a run, the stored thread is complete, but the changes are not in the saved book.

6Approval (interrupt and resume)

Some plans need the approval of the user before the server applies them. The rule is in needs_approval (agui.py:183):

  • The plan deletes one or more pages.
  • The plan changes more than 3 pages (APPROVAL_PAGE_LIMIT). A text edit counts for the page that contains the text.

A change of theme or of the style of all text of one role does not need approval. These changes do not change words or photos, and one undo step removes them.

The approval decision is a new run. Its resume field contains {interruptId, status, payload: {approved}}. _resume (agui.py:423) does these checks:

  1. It compares interruptId with the stored pending interrupt. If they are different, the run stops with RUN_ERROR code unknown_interrupt.
  2. It reads the plan from the database. It does not use a plan from the browser.
  3. It applies the plan only if status is resolved and approved is exactly true. Each other value keeps the book as it is.
WARNINGDo not apply a plan that the browser sends in a resume request. A changed browser can send any plan. The server must use only the plan that it stored.

7Thread and history

The server keeps the thread of each book in the table agent_threads (storage.py:193). A row has the messages and the pending approval, if there is one.

  • When the chat panel opens, it gets the thread with GET /api/agent/threads/{id} (app.py:198). It also gets an open approval request.
  • The browser sends only the new message in each run. The server adds the stored messages.
  • The model gets the last 12 text turns (HISTORY_LIMIT). Thus a request such as "make it shorter" refers to the last change.
  • The server keeps a maximum of 200 messages for each thread (THREAD_MESSAGE_LIMIT).

8Frontend tool

A frontend tool is a tool that the browser does, not the server. The chat panel offers one tool: show_page (ChatPanel.tsx:9). It turns the editor to a page.

  1. The browser sends the tool definition in tools.
  2. After the changes, the server sends a show_page tool call with the last changed page. It does not send the call if the editor shows that page already.
  3. The browser turns the editor to that page (onToolCallEndEvent).
  4. The browser adds the tool result to the thread. The next run sends this result to the server.

The server sends this tool call only when the browser offered the tool.

9Errors

A failed run stops with a RUN_ERROR event. The book in the editor does not change. Table 3 gives the error codes.

CodeCauseMessage to the user
bad_inputThe book in the state is not valid.The book sent with this request is not valid.
bad_inputThe request has no user message.Send a message describing the change you want.
unknown_interruptThe approval request is not open now.This approval request is no longer open.
ai_errorThe model did not give a usable plan.The AI couldn't make that change. Your book is unchanged.
internalAn unexpected error on the server.Something went wrong on our side.

Table 3. Error codes

If the model call fails, the server removes the partial reply from the thread. The cause can be a stream that stops, or a plan that is not valid. Then the server tries the offline rules. The offline rules can do structural changes only, for example a theme change. They cannot write new text. If the offline rules find no change, the run stops with ai_error.

  1. The behaviour — tests/test_agui.py

    Start here. The tests show what a run must do, without the details of the code.

    • test_run_streams_reply_reasoning_activity_and_snapshot (line 63): the event sequence of Figure 2.
    • test_approval_interrupt_then_resume (line 100): the interrupt and the resume of Figure 4.
    • test_cancel_and_superseded_approvals (line 140): cancel, and a new message that replaces the pending plan.
    • test_frontend_tool_show_page_when_offered (line 212): the frontend tool.
    • test_failures_become_run_errors (line 224): the error codes of Table 3.

  2. The endpoint — src/memory_book/app.py

    Lines 191–202. Approximately 10 lines.

    • POST /api/agent: FastAPI validates the body as RunAgentInput. EventEncoder changes each event to one SSE line.
    • GET /api/agent/threads/{id}: the stored thread and the open approval.

  3. The run — src/memory_book/agui.py, part 1

    Read the docstring at the top first (lines 1–21). It gives the event sequence. Then read lines 335–474.

    • run_agent (335): the run goes in a worker thread. The events go through a queue to the HTTP response.
    • _run (356): validates the book, loads the thread, selects _request or _resume, saves the thread and sends the last events.
    • _request (399): gets the plan, examines the approval rule, then applies or stops.
    • _resume (423): the three checks of paragraph 6.
    • _apply (439): one tool call, one STATE_DELTA and one ACTIVITY_DELTA for each operation.

  4. Events and patches — src/memory_book/agui.py, part 2

    Lines 90–330.

    • Output (230): makes the AG-UI events. It also keeps the messages for the thread. model_output receives the tokens from the model.
    • json_diff (90): the id-aware JSON Patch of paragraph 5.
    • needs_approval (183) and describe (154): the approval rule and the checklist labels.

  5. The plan types — src/memory_book/ai.py

    Lines 122–202.

    • The Op* classes, for example OpSetText and OpDeletePage: the only operations that the model can ask for.
    • RevisionPlan: the summary and the list of operations. The model must give JSON that agrees with this schema.

  6. Plan and apply — src/memory_book/pipeline.py

    Lines 191–330.

    • plan_revision (310): sends the book summary and the request to the model. If the model fails, it tries the offline rules (paragraph 9).
    • apply_revision (191): applies the operations to the book. It skips an operation with an unknown identifier and tells why.

  7. The thread store — src/memory_book/storage.py

    Lines 193–205, and the table agent_threads in SCHEMA.

    • get_thread and save_thread: the messages and the pending plan of each book.

  8. The client — web/src/editor/ChatPanel.tsx

    All of the file, approximately 220 lines.

    • Line 57: new HttpAgent({ url: '/api/agent', threadId }).
    • Line 71: loads the stored thread when the panel opens.
    • Line 99: agent.runAgent(…) with the callbacks onStateChanged, onToolCallEndEvent and onRunFinishedEvent.
    • Line 141: decide() sends the approval decision as resume.
    • ChecklistView: shows the activity checklist.

Do this procedure to see the events of a run on your computer. The procedure uses the offline provider. It does not use an API key.

  1. Start the database and the storage: docker compose up -d db rustfs mlflow.
  2. Open tests/test_agui.py. Find test_run_streams_reply_reasoning_activity_and_snapshot.

  6. Remove the print line.
CAUTIONDo not use the real model for this exercise. Each run with the real model uses tokens and costs money.

11Observability

Each run is one MLflow trace with the name agent_run (agui.py:372). The trace contains these spans:

  • plan_revision, with one CHAT_MODEL span for each model call. These spans keep the token usage and the cost.
  • One TOOL span for each operation, with its result.

The trace has the session book-<id>. Thus the MLflow "Sessions" view shows all AI work for one book. The token usage also goes to the browser in RUN_FINISHED.usage. The chat panel shows it below the reply.

For more data, refer to docs/memory-book-report.html, paragraph 5.
