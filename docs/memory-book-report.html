1Introduction

1.1 Scope

The Memory Book system makes personal photo books. The user gives photos and notes. The AI writes the text and puts the pages in order. The user then changes the book, reads the book and exports the book as a PDF file.

This document is for software engineers and operators. It does not give user instructions for the editor controls.

1.2 Writing rules in this document

  • Sentences in procedures have a maximum of 20 words. Descriptive sentences have a maximum of 25 words.
  • Each step in a procedure has one instruction. Instructions use the imperative form.
  • Words in code font are technical names. Words in quotation marks are labels on the screen. These names do not change.
  • A WARNING tells you about a risk to data or security. A CAUTION tells you about a risk to the system.

1.3 Terms

2System description

2.1 Function

The system has one document model. The editor, the reader and the PDF renderer use the same document. Thus, the screen and the printed page agree.

The AI makes structured data only. The AI does not write user interface code. A layout engine in code calculates all positions.

2.2 Architecture

2.3 Data flow for a new book

  1. The user uploads photos. The app keeps the original file and makes a preview and a thumbnail.
  2. The AI reads the photos and the notes. It makes a MemoryAnalysis: events, captions and photo importance.
  3. The AI makes a StoryPlan: chapters, text, and one template name for each page.
  4. The code checks the plan. It removes unknown photo IDs and duplicate photos.
  5. The layout engine changes the plan into pages with positioned elements.
  6. The app checks the book against the schema and records it in PostgreSQL.

2.4 AI models (LiteLLM)

The app sends all AI requests through LiteLLM. LiteLLM connects to many providers with one interface, for example Google, OpenAI, Anthropic and local Ollama models.

  • Each request has a strict JSON schema. All fields are necessary, and the theme fields accept only the real theme names.
  • Some providers do not write fields that are not necessary. Without the strict schema, the result can be empty.
  • The app checks each result again with Pydantic. An empty analysis or an empty plan is a failure.
  • LiteLLM uses its local price list. It does not download data when the app starts.
WARNINGLiteLLM versions 1.82.7 and 1.82.8 contained malicious code (advisory MAL-2026-2144). The project uses version 1.104.0 exactly. The file uv.lock contains the hash of each package file. Before you change the version, examine the advisories in the OSV database.

4Chat editing (AG-UI)

4.1 Function

The chat lets the user change the book with words. The user does not have to move elements or use menus. The system uses the AG-UI protocol, version 1.0.

Streamed reply

The reply shows word by word while the AI writes the plan. The server decodes the reply from the partial JSON.

Visible reasoning

The AI sends a summary of its thinking. The chat shows it under “How I approached this”.

Approval

Before the AI removes pages or changes more than three pages, it stops and asks the user.

Live changes

The page on the canvas changes during the run. The client receives a small state delta after each operation.

Progress checklist

An activity message shows each planned change. Each item shows a check mark when the server applies it.

Server threads

The server keeps the conversation. The history stays after a reload or on a different device.

Token usage

RUN_FINISHED contains the tokens for each model. The chat shows the total under the reply.

One undo step

A full run is one step in the undo history. The chat shows an “Undo these changes” button.

Frontend tool

The agent can call show_page. The editor then turns to the page that changed.

4.2 Run input (POST /api/agent)

The request body is an AG-UI RunAgentInput. The response is a stream of server-sent events (text/event-stream).

FieldValue from the Memory Book client
threadIdbook-<book id>. One chat thread for each book.

state{"book": MemoryBook}. This is the current book in the editor. The server checks it against the schema.

contextOne item, editor-focus, with pageId and elementId as JSON.
resumeOnly for an approval decision: [{interruptId, status, payload}]. The status is resolved or cancelled.

4.4 Approval (interrupts)

Some plans can remove much work. For these plans, the agent stops and asks the user. The book does not change until the user approves.

ConditionResult
The plan contains delete_pageApproval is necessary.
The plan changes more than three pages (APPROVAL_PAGE_LIMIT)Approval is necessary.
All other plansThe agent applies the plan at once.

When approval is necessary, the server sends events 1 to 5. Then it sends an ACTIVITY_SNAPSHOT with the status proposed, a MESSAGES_SNAPSHOT and RUN_FINISHED. The outcome of RUN_FINISHED is interrupt:

{"type":"interrupt","interrupts":[{"id":"…","reason":"approval_required",
  "message":"This removes 2 pages. Do you want to apply these changes?",
  "responseSchema":{"type":"object","properties":{"approved":{"type":"boolean"}}}}]}
  • The server keeps the plan in the thread record. The client does not send the plan back. Thus, the client cannot change an approved plan.
  • The decision is a new run with resume. With resolved, the server applies the stored plan to the current book. With cancelled, the book does not change.
  • A new user request closes an open approval. An old or unknown interrupt ID gets RUN_ERROR with the code unknown_interrupt.
  • An open approval stays after a reload. GET /api/agent/threads/{id} sends it to the client.

4.6 Thread storage

The server keeps each thread in the PostgreSQL table agent_threads. The thread contains AG-UI messages with these roles:

RoleContent
userThe request of the user.
reasoningThe thinking summary of the model.
assistantThe reply, and the tool calls that the reply started.
activityThe checklist of the changes, with its last status.
toolThe result of each tool call. The client sends the results of show_page.
  • The model receives the last 12 user and assistant turns (HISTORY_LIMIT). Thus, “make it shorter” refers to the last subject.
  • The server keeps the newest 200 messages of a thread (THREAD_MESSAGE_LIMIT).
  • If a run fails, the server keeps the user message. The user can then try again.

4.7 State deltas

The server compares the book before and after each operation. It sends the difference as a JSON Patch.

  • Lists of objects with an id field are compared by ID. These lists are pages, elements and chapters.
  • A new page gives one add operation. A removed page gives one remove operation. A moved page gives one move operation.
  • Other lists are compared by position. If the length changes, the server replaces the list. These lists are short, for example the photo IDs.

The test test_json_diff_round_trips_and_matches_lists_by_id applies each patch and compares the result with the server book.

4.8 Client behavior

  • The client uses HttpAgent from @ag-ui/client. The agent applies each state delta, activity delta and messages snapshot.
  • When the chat opens, the client reads the thread and any open approval from the server.
  • The editor puts each new book state into the undo history with the key agent:<runId>. Thus, one run is one undo step.
  • During a run, the canvas, the page list and the keyboard commands are locked. This prevents conflicts with the patches.
  • The approval card has two buttons: “Apply changes” and “Keep the book as it is”. Each button starts a run with resume.
  • The “Stop” button stops the client stream (abortRun). The server completes the run and keeps the result in the thread.
  • The client sends the result of show_page after the run. Thus, the next run has a complete thread.
  • The prompt bar below the canvas sends its text through the same chat.
  • The autosave function records the changed book in the database after 1.2 seconds.

If the model call fails, the server tries the fallback models, then the offline rules. Before it uses the offline rules, it removes the part of the reply that the model streamed. If the offline rules cannot do the request, the client receives RUN_ERROR.

4.10 Limits of the AG-UI integration

  • The approval rule is fixed in the code. The user cannot change the limit of three pages.
  • The client always sends the full book as state. The server does not send STATE_SNAPSHOT.
  • Each run uses one server thread. If the client stops the stream, the run continues to the end.
  • The chat accepts text only. It does not accept photos or files in a message.
  • The agent does not use sub-agents, so it sends no SUBAGENT_* events.

5AI observability (MLflow)

The app sends traces to MLflow when MLFLOW_TRACKING_URI is set. Without this value, the trace functions do nothing.

5.1 Trace structure

Book generation

generate_book        AGENT
├─ understanding     CHAIN
│  └─ llm.MemoryAnalysis     CHAT_MODEL
├─ organizing        CHAIN
├─ story             CHAIN
│  └─ llm.StoryPlan          CHAT_MODEL

Chat run

agent_run            AGENT
├─ plan_revision     CHAIN
│  └─ llm.RevisionPlan       CHAT_MODEL
├─ set_theme         TOOL
└─ apply_template    TOOL

An approval run has only agent_run and the TOOL spans. The attribute resume is true.

8Procedures

8.1 Start the system

WARNINGThe default passwords of PostgreSQL and RustFS are public. Change them before you connect the system to a public network.
  1. Install Docker with Docker Compose.
  2. Optional: copy .env.example to .env.
  3. Optional: write your model key in .env, for example after GEMINI_API_KEY=.
  4. In the project folder, type docker compose up --build.
  5. Wait until all four services are healthy.
  6. Open http://localhost:8000 in a browser.

8.2 Make a new book

  1. Click “Start a new book”.
  2. Upload the photos.
  3. Write some words about the memory.
  4. Optional: open “Details and style” and set the title, theme, size or length.
  5. Click “Create my book”.
  6. Wait until the editor opens.

8.3 Change a book with the chat

  1. Open the book in the editor.
  2. Select the “Chat” tab.
  3. Optional: go to the page that you want to change.
  4. Write the request, or click a suggestion.
  5. Press Enter.
  6. Examine the changes on the canvas and in the checklist.
  7. If you do not like the result, click “Undo these changes”.

8.4 Approve or cancel a large change

CAUTIONApproved changes can remove pages. Read the list of proposed changes before you click “Apply changes”.
  1. Read the question in the approval card.
  2. Read the items under “Proposed changes”.
  3. To apply the plan, click “Apply changes”.
  4. To keep the book, click “Keep the book as it is”.
  5. Optional: after you apply, click “Undo these changes” to go back.

8.5 Export a PDF file

  1. Click “Export PDF”.
  2. Select “For reading and sharing” or “For a print shop”.
  3. Click “Create PDF”.
  4. Read the warnings, if there are warnings.
  5. Click “Download PDF”.

8.6 Do the tests

CAUTIONThe Python tests need the services db, rustfs and mlflow. Start them before you start the tests.
  1. Type docker compose up -d db rustfs mlflow.
  2. Type uv run pytest.
  3. Go to the web folder.
  4. Type npm test.
  5. Type npx tsc -b and npm run lint.

10Known limits

  • The live tests used gemini/gemini-3.8-flash. The other providers were tested with simulated LiteLLM responses only.
  • The provider sends the reply in large parts. For Gemini Flash, one reply arrives in approximately two parts.
  • The system has no user accounts. All users of one installation see all books and all threads.
  • Background jobs and chat runs use threads in the app process. If you start more than one app process, use a job queue.
  • The app sends photos through its own process. For high traffic, use signed S3 links.
  • The map page shows a decorative map. It does not show real map data.
  • The database schema is made at start-up. A schema change will need a migration tool.
  • For the limits of the chat, refer to paragraph 4.10.
